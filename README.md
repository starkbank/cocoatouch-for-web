# CocoaTouch for Web

Apple's CocoaTouch, UIKit and Foundation, for the browser. Write a page as a `UIViewController` with `@IBOutlet` and `@IBAction` bindings and a `.xib` holding its html, the way you would in Xcode, and run it on jQuery.

```
src/uipages/home/
    index.js                 imports the other three files, exports the controller
    homeViewController.js    export class HomeViewController extends UIViewController
    homeViewController.css
    homeViewController.xib   plain html, attached to HomeViewController by name at build time
```

```js
import "UIKit"


export class HomeViewController extends UIViewController {

    @IBOutlet("#title", UILabel) titleLabel
    @IBOutlet("#open", UIButton) openButton

    viewDidLoad() {
        this.titleLabel.text = "Hello"
    }

    @IBAction("#open", UIButton) openButtonTapped(sender) {
        window.location.href = "/api"
    }

    @IBAction(UIKeyModifierFlags.command + UIKeyCommand.input("k")) commandKPressed() {
        window.location.href = "/search"
    }
}
```

## Install

```
npm install cocoatouch
```

`import "UIKit"` works like Swift's `import UIKit`: the framework's classes become ambient in the page, so files use `UIViewController`, `UILabel` or `@IBOutlet` unqualified. Point webpack at the framework names once:

```js
// webpack.config.js
resolve: {
    alias: require("cocoatouch/webpack/aliases"),
}
```

The same goes for `import "Foundation"`, `import "CoreGraphics"`, `import "CoreAnimation"`, `import "CoreMedia"`, `import "AVKit"` and `import "UniformTypeIdentifiers"`; `import "UIKit"` brings Core Graphics along, as it does in Swift. Named imports work too, from `"cocoatouch"` or from a framework entry such as `"cocoatouch/UIKit"` (PDFKit's names come only from `"cocoatouch/PDFKit"` or `import "PDFKit"`). The lowercase entries `cocoatouch/uikit` and friends export the same classes without touching globals.

Requirements:

- jQuery 3 available as the global `$` before the bundle runs.
- Babel with `@babel/plugin-proposal-decorators` in `legacy` mode and `@babel/plugin-proposal-class-properties`, for `@IBOutlet` and `@IBAction` in your own classes. The framework itself is plain ES2022, except the PDFKit entry, which imports a `.css` file and writes `new Worker(new URL(...))`.
- For PDFKit only, besides what §PDF asks of the server and of a stylus rule: webpack 5, for the `new Worker(new URL(...))` worker chunk, and a CSS rule able to handle a `.css` imported from `node_modules` (the sample uses `style-loader` plus `css-loader`).
- A `<cocoatouch></cocoatouch>` element in the page. Controllers present into it.

## Nibs

A `.xib` is the html of one view. The webpack loader attaches it to the class of the same name exported by the sibling `.js`, so `codeView.xib` becomes `CodeView.nib`. The link is an import emitted at build time, which survives minification.

```js
// webpack.config.js
{
    test: /\.xib$/,
    use: ["babel-loader", require.resolve("cocoatouch/webpack/xibLoader")],
}
```

A `.xib` without a sibling `.js`, or whose sibling does not export a class of that name, fails the build with a message naming both files.

A view's nib describes the view's contents when the view has a host element, and the view itself when it does not. A view owns one element, and its nib fills that element. For a view declared as an `@IBOutlet`, the element is the one the outlet names in the owner's nib, so its own nib may have any number of top-level elements: they become the view's children, the way a xib's objects become a view's subviews. For a view created in code and placed with `addSubview`, there is no element yet: a nib with one root makes that root the view's element, so the classes the superview lays out by go on it; a class nib with several roots, or with stray text beside its root, throws with the root count and an excerpt of the nib, since a plain `<div>` wrapper is one the stylesheet cannot address. Give a view you create in code a single root. An empty class nib and `UIView.loadFromNib(html)` with several roots still get the wrapper.

A nib configures the view it draws through `@IBInspectable`, Interface Builder's user-defined runtime attributes: `@IBInspectable title` reads `data-title` off the view's own element into `title`, `@IBInspectable(UIColor) titleColor` reads `data-title-color` and converts it, and the value lands after the outlets are connected and before `awakeFromNib`, so `awakeFromNib` sees the configured view. The name maps lowerCamelCase to dashes. The types are the ones Interface Builder inspects: `String` (the default), `Number`, `Boolean` (`"true"` or `"false"`, anything else throws), `UIColor` (`#…` is a hex color, any other value a token resolved like `UIColor(named:)`), `UIImage` (`UIImage(named:)`), `CGPoint` and `CGSize` (two comma-separated numbers) and `CGRect` (four). A malformed number or boolean throws, naming the property; an absent attribute leaves the field's declared default standing.

Since 1.8.1 a class's outlets are resolved in one walk of its element instead of one query each, so binding cost no longer grows with the outlets times the page: an outlet written as a bare id, class or tag is answered from that walk, any other selector keeps jQuery's own lookup, and a view the framework is constructing is handed the element its creator already found. The elements an outlet binds are the ones `find` returns.

Since 1.9.0 an outlet collection is Swift's `@IBOutlet var chips: [UILabel]!`, written with the class in an array: `@IBOutlet(".chip", [UILabel]) chips` binds one `UILabel` per element the selector matches inside the owner, in document order, and `chips` is that array (empty when nothing matches). Each element is bound as a single outlet is: it is a subview of the owner, its own outlets, inspectables, `awakeFromNib` and actions follow, and `restore` rebinds it with `didMoveToWindow`. The array is whole before the first element is awakened, so an element can read its siblings. An element without an id is given `<owner id>-<property>-<position>`. One element has one owner: a collection over an element another outlet of the same owner already holds throws a `TypeError` naming both, before anything is bound; elements a different owner holds, such as the previous cell of a reused row, are taken over as for a single outlet. The array must hold exactly one class.

A class may define accessors named `value`, `get`, `set` or `initializer` beside its outlets and actions. `@IBOutlet` and `@IBAction` hand Babel's legacy decorator transform a plain descriptor (a field's has no initializer, a method keeps its own) instead of the prototype, which the transform reads those four names off, so none of the class's accessors runs while it is defined. `test/fixtures/babel/valueView.js` is a class compiled by the apps' Babel setup that the suite loads to keep this true.

```js
export class BannerView extends UIView {

    @IBInspectable title = "Untitled"
    @IBInspectable(UIColor) titleColor = UIColor.black
    @IBInspectable(Boolean) isWide = false

    awakeFromNib() {
        this.titleLabel.text = this.title
        this.titleLabel.textColor = this.titleColor
    }
}
```

```html
<div id="hero-banner" data-title="Pix" data-title-color="accent-color" data-is-wide="true"></div>
```

## Lifecycle

```
present(controller, {animated})   viewDidLoad -> viewWillAppear(animated) -> viewWillLayoutSubviews -> viewDidLayoutSubviews -> viewDidAppear(animated)
                                  the previous root controller and its tree first get viewWillDisappear(animated) -> viewDidDisappear(animated)
restore(controller)               rebinds outlets and actions on pre-rendered html: viewWillAppear(false) -> viewDidAppear(false), never viewDidLoad
resize                            viewWillTransition -> viewWillLayoutSubviews -> layoutSubviews on every view -> viewDidLayoutSubviews
```

`animated` is the flag `present` was given, `false` by default, on `restore` and for an embedded child; an override that declares no parameter keeps working. `restore` sends no layout pair, since the html it rebinds is already laid out; the views' `layoutSubviews` runs on resize, between the controller's layout pair. `loadView()` is not provided: `view` is created by the framework and the nib injected before any hook runs, so an override could neither create nor replace it.

Views get `awakeFromNib` after their outlets are bound, `layoutSubviews` once their element is in place and `didMoveToWindow` when their element enters the page, by `addSubview` or when a pre-rendered page is restored. `addSubview(view)` sends, in this order: `willMove({toSuperview})`, the insertion, `didMoveToSuperview()`, `didMoveToWindow()`, outlet binding, action connection, inspectable binding, `awakeFromNib()`, `layoutSubviews()`; `removeFromSuperview()` sends `willMove({toSuperview: null})` before the removal and `didMoveToSuperview()` after, and no `didMoveToWindow`. Three deviations from UIKit, on purpose: `awakeFromNib` follows the insertion here, where UIKit awakes nib objects before inserting them, so a body may measure or style the element; `didMoveToWindow` here means "entered the page", where Apple also sends it on removal when the window becomes `nil`; and the superview pair coming before the window hook is this package's order, which Apple's reference does not document, pinned by a test. `willMove(toWindow:)` is not provided: the page has one `UIWindow`, so there is no window for a view to move to, and `didMoveToWindow` already says "entered the page". `addInteraction(interaction)` sends the interaction `willMove({to: view})`, adds it, then sends `didMove({to: view})`; `removeInteraction` sends `willMove({to: null})`, removes it, then `didMove({to: null})`, and a `UIToolTipInteraction` draws its attribute in `didMove` and erases it in `willMove` to nil. `addSubview` links the child into the responder chain, so `view.next`, `view.superview` and `view.subviews` work; a view reaches its controller the way it does on iOS, by walking `next` until a `UIViewController` answers.

`awakeFromNib` is sent exactly once, and only after the view is fully initialised. A view owns its element, so an `@IBAction` naming a class over an element that an outlet, a cell, an `addSubview` or the app's own constructor already bound is a second connection to that view and awakes nothing. A view the framework creates, as an outlet, a dequeued cell or a subview placed with `addSubview`, is bound and awoken by its creator once `new` has returned, so its class fields hold their declared values inside `awakeFromNib`. Three consequences. `init()` runs before the subclass's field initialisers in every case, since it is called from `UIView`'s constructor. A view the app constructs on an existing empty element, `new SecureTextField("#password")`, is bound and awoken by its own constructor, so there `awakeFromNib` runs before the subclass's fields; a class that needs its own fields in `awakeFromNib` should be created without a selector and placed with `addSubview`. And a subclass must pass the selector it receives to `super` unchanged, or the framework will treat it as an app-constructed view and bind it in its constructor as well as in its creator.

## Lifecycle order

What each path sends, in order. A test asserts every sequence below with `deepEqual`.

- **`present(controller, {animated})`**: the previous root controller's tree gets `viewWillDisappear(animated)` (container, children depth-first, outlet-bound controllers), is disposed, then gets `viewDidDisappear(animated)` in the same order; then the new controller's outlets awake (`awakeFromNib`), and it gets `viewDidLoad`, `viewWillAppear(animated)`, `viewWillLayoutSubviews`, `viewDidLayoutSubviews`, `viewDidAppear(animated)`, then `completion`. A root swap is sequential, the old controller's pair before the new one's, not interleaved as a modal transition would be.
- **`restore(controller)`**: the same disappear pair for the previous root; then each outlet gets `didMoveToWindow` in place of `awakeFromNib`; then `viewWillAppear(false)`, `viewDidAppear(false)`. One rule, for the root and for controllers bound as outlets: `restore` sends the did-move and appear hooks, never the load hooks — the prerenderer loaded, the client appears, and a `viewDidLoad` that builds content would duplicate the html it is restoring into. `isViewLoaded` is true all the same. No layout pair, since the html is already laid out.
- **A controller bound as an `@IBOutlet`**: `awakeFromNib`, `viewDidLoad`, `viewWillAppear(false)`, `viewDidAppear(false)`, right after its own outlets, inspectables and actions are bound and before its host's `viewDidLoad`; on restore, `didMoveToWindow`, `viewWillAppear(false)`, `viewDidAppear(false)`, following the restore rule; it is not one of the host's `children` and its `parent` is `null`; it gets `viewWillTransition` and the trait hooks on resize, and the disappear pair when its host goes.
- **Containment**: `addChild(child)` sends `willMove({toParent})`; `container.addSubview(child.view)` then sends `viewDidLoad`, `viewWillAppear(false)`, `viewWillLayoutSubviews`, `viewDidLayoutSubviews`, `viewDidAppear(false)`, `didMove({toParent})`. `removeFromParent()` sends `willMove({toParent: null})`, then `viewWillDisappear(false)` and `viewDidDisappear(false)` to the child and its own children, then `didMove({toParent: null})`. Unlike Apple, where `addChild` sends only `willMove` and `removeFromParent` only `didMove` and the caller sends the other, the framework sends all four, so a caller following Apple's guidance and sending one itself sends it twice.
- **A sender class named by `@IBAction`**: the element each action matches, when no view owns it yet, is bound like an outlet, in this order: its own outlets, its own actions' senders by the same rule, inspectables, `awakeFromNib`. Actions are connected before `awakeFromNib`, as Interface Builder orders it, so `awakeFromNib` can `sendActions` to them. An element a view already owns gets its sender built and handed to the handler and nothing else, no hook; if the sender class carries a nib and is not the class that owns the element, the action is refused with a `TypeError`. On `restore` the order is the restore one: its outlets' `didMoveToWindow`, its own actions' senders, inspectables, `didMoveToWindow` in place of `awakeFromNib`. A plain `UIButton` sender has none of these and receives nothing.
- **`addSubview(view)`**: `willMove({toSuperview})`, the insertion, `didMoveToSuperview()`, `didMoveToWindow()`, outlet binding, action connection, inspectable binding, `awakeFromNib()`, `layoutSubviews()`. `awakeFromNib` follows the insertion here, unlike UIKit, so a body may measure; the superview pair before the window hook is this package's order, Apple not documenting the interleaving.
- **`removeFromSuperview()`**: `willMove({toSuperview: null})`, the removal, `didMoveToSuperview()`. No `didMoveToWindow`: here it means "entered the page", where Apple also sends it on removal.
- **Application activity**: UIKit's load makes the application and its one `UIWindow` (see `UIApplication.shared` under Controls), and a document that already has them, from a second copy of the package, keeps them. A page that loads visible is `.inactive` and posts `didBecomeActive` once, with `.active`, at the first task after load. A hidden page posts `willResignActive` with `applicationState` `.active`, then `didEnterBackground` with it `.background`; a page that becomes visible posts `willEnterForeground` with `.background`, then `didBecomeActive` with `.active`. A page hidden before the launch task posts `didEnterBackground` alone and the task never posts. A page that loads hidden starts `.background`, posts nothing at load and posts only the second pair when it is shown; a repeated visibility event posts nothing. A test asserts the four, and the launch, with `deepEqual`, and asserts that evaluating the entry twice on one document installs one listener and launches once.
- **Resize**: when the size classes change, `willTransition({to, with})` on every controller first; then per controller `viewWillTransition({to, with})`, its children, `traitCollectionDidChange(previous)` on it and its views (only on a change), `viewWillLayoutSubviews`, `layoutSubviews()` on every view, `viewDidLayoutSubviews`.

## Child view controllers

A controller composes others the way UIKit's containment API does: add the child, then put its view in one of your container views. The container element becomes the child's root, its nib fills it, its outlets and actions bind inside it and `viewDidLoad -> viewWillAppear -> viewDidAppear` run. Removing the child empties the container, runs `viewWillDisappear -> viewDidDisappear` and releases the observers it registered.

```js
class OnboardViewController extends UIViewController {

    @IBOutlet("#content", UIView) contentView

    show(step) {
        if (this.current) { this.current.removeFromParent() }
        this.current = new step()
        this.addChild(this.current)
        this.contentView.addSubview(this.current.view)
    }
}
```

A `UIViewController` declared as an `@IBOutlet` is a container view in all but name: once its outlets, inspectables and actions are bound it receives `awakeFromNib` (when defined), then `viewDidLoad`, `viewWillAppear`, `viewDidAppear`; on a restored page it receives `didMoveToWindow` in place of `awakeFromNib` and no `viewDidLoad`, as `restore` sends the did-move and appear hooks and never the load hooks; it gets `viewWillTransition` and the trait hooks on resize, and the disappear pair when its host goes. It is not one of the host's `children` and its `parent` is `null`.

`children`, `parent`, `willMove({toParent})` and `didMove({toParent})` follow UIKit. A plain view's `removeFromSuperview()` takes its element out of the page. A container forwards the disappear pair, as UIKit's automatic forwarding does: when the root controller is swapped by `present`, or an embedded child is removed, `viewWillDisappear` goes to the container first, then to its children depth-first, then to the controllers bound as its outlets; the tree is disposed; then `viewDidDisappear` follows the same order, after which each disposed child's `parent` is `null` and the container's `children` is empty.

## Navigation

`UINavigationController` is a stack of controllers bound to browser history: a navigation stack and the session history are the same data structure, so the binding is a mapping, not a simulation. The stack is the page's root — `navigationController.present(navigationController)` — and its nib is a `navigationBar` above a content container. Each entry gets a host view of its own: a push adds a fresh empty host, embeds the new controller into it and hides the previous host (`isHidden`), so the controller below keeps its element and is never reloaded; a pop removes the popped controller's host and shows the one below again.

```js
var navigation = new UINavigationController({rootViewController: new ListViewController()})
navigation.present(navigation)
this.navigationController.pushViewController(new DetailViewController(), {animated: true})
this.navigationController.popViewController({animated: true})
```

`viewControllers` (get and set), `setViewControllers(_:animated:)`, `topViewController`, `visibleViewController`, `pushViewController(_:animated:)`, `popViewController(animated:)` (returns the popped controller, `null` on a one-deep stack, since Apple refuses to pop the root), `popToRootViewController(animated:)` and `popToViewController(_:animated:)` (return the popped controllers in stack order), `delegate`, `navigationBar`, `isNavigationBarHidden` and `setNavigationBarHidden(_:animated:)`; every controller has `navigationController` (`null` outside a stack) and a `navigationItem` with `title` and `hidesBackButton`. The delegate gets `navigationControllerWillShowViewControllerAnimated(nav, viewController, animated)` and `navigationControllerDidShowViewControllerAnimated(nav, viewController, animated)`.

**History.** `pushViewController` calls `history.pushState({cocoatouchNavDepth: n}, "", url)`, the url being the pushed controller's `userActivity.webpageURL` or none, in which case the address does not move; `popViewController` mutates the stack synchronously, returns, then goes back one history entry, and the resulting `popstate` finds nothing left to pop. The browser's back button pops the stack. `popstate` only ever pops: the stack cannot know what a forward entry held, so **the forward button does not restore a popped controller**, and a fresh load on a pushed address has no stack — the app's own routing rebuilds one with `setViewControllers`, as the sample does. A router that presents on `popstate` must leave to the stack the addresses the current stack serves.

**Order on a push of B over A**, sequential as a root swap is: `A.viewWillDisappear(animated)`, `A.viewDidDisappear(animated)`, A's host hidden, `B.willMove({toParent})`, `B.viewDidLoad`, the delegate's `willShow`, `B.viewWillAppear(animated)`, `B.viewWillLayoutSubviews`, `B.viewDidLayoutSubviews`, `B.viewDidAppear(animated)`, `B.didMove({toParent})`, the delegate's `didShow`. **On a pop of B back to A**: `B.viewWillDisappear`, `B.viewDidDisappear`, `B.willMove({toParent: null})`, `B.didMove({toParent: null})`, B's host removed, A's host shown, `willShow`, `A.viewWillAppear`, `A.viewWillLayoutSubviews`, `A.viewDidLayoutSubviews`, `A.viewDidAppear`, `didShow` — and no second `viewDidLoad` for A. `popToRootViewController` and `popToViewController` send the disappear pair to each popped controller, deepest first, then one appear pair to the destination.

**What is not provided, by design**: the interactive pop gesture; UIKit's transition animation — `animated` reaches the hooks and the delegate, and the content container carries the `animated` class for the stylesheet to transition, nothing more; `hidesBottomBarWhenPushed`; custom transitions; forward-button restore after a pop; automatic deep-link stack rebuilding; `UIBarButtonItem` and bar customisation — the bar draws Apple's default back button, titled after the previous controller's `navigationItem.title` and suppressed by `hidesBackButton`, and is visible by default as on iOS. While a stack is root, `present` still means "become the page's root controller" and destroys the stack; inside a stack, push.

## Animations

`isHidden = false` shows the view whatever hid it: it removes the inline value, and when the stylesheet still hides the element it writes the display the element has by nature (`table-cell` for a `td`, `table-row` for a `tr`, `list-item` for an `li`, `inline` for a `span`, `block` for anything else). A stylesheet that owns an element's visibility, a responsive rule for one, is not driven through `isHidden`.

`UIView.animate` runs property changes over a duration: `alpha` and `isHidden` fade instead of switching. `UIView.transition` swaps two views, sliding the new one in from the side named by a flip option or dissolving it.

```js
const card = UIView.loadFromNib(html)
this.listView.insertSubview(card, {at: 0})
card.alpha = 0
UIView.animate({withDuration: 0.5, animations: () => { card.alpha = 1 }})

UIView.transition({from: this.searchView, to: this.passwordView, duration: 0.28, options: [UIView.AnimationOptions.transitionFlipFromRight]})
```

`insertSubview(view, {at})` places a view's nib inside another view without restyling it; `tag` keeps an integer on a view; `accessibilityIdentifier` reads or sets a view's element id; `accessibilityLabel` reads or sets the element's `aria-label`, and the `alt` of an `<img>`; an outlet matched by class is given `<owner id>-<outlet name>` and a subview added in code `<superview id>-<n>`, so nib-drawn views stay addressable without the app naming them; `UIControl.sendActions({for})` fires a control event; key commands reach the deepest bound responder that contains the focused element first and climb to the enclosing ones only when the handler returns `false`; and a view class with a `.xib` fills the empty element it is created on, so `new SecureTextField("#password")` renders like the outlet would.

**Accessibility.** The framework writes the ARIA attributes and app code never does. `view.accessibilityExpandedStatus` (`UIAccessibility.ExpandedStatus`: `unsupported` 0, `expanded` 1, `collapsed` 2, iOS 18) is `aria-expanded` `"true"` or `"false"`, and `unsupported`, the default, removes it. `view.accessibilityValue` (`String?`) is `aria-valuetext`; `null`, and an empty text, remove it. `view.accessibilityTraits` is an array of `UIAccessibilityTraits` cases (`button`, `link`, `header`, `selected`, `notEnabled`; `UIAccessibilityTraits.none` is the empty array): `button`, `link` and `header` draw `role` `button`, `link` and `heading` only where the element's native role differs, so a `<button>`, an `<a href>` and an `<h1>` to `<h6>` get nothing for the trait they already are, and when several want the role the most specific wins (header, then link, then button); a heading's `aria-level` is not set, so it reads at the default level. `selected` has one rule: an item under a `listbox`, `tablist`, `grid`, `treegrid` or `tree` is `aria-selected="true"`, a toggle-like control (a `<button>` or `role="button"`) is `aria-pressed="true"`, and any other element has no ARIA state for it and draws nothing; leaving the set removes the attribute rather than writing `false`. `notEnabled` is `aria-disabled="true"` on a view that is no control: a control's `isEnabled` already draws `disabled`, and a trait never changes `isEnabled` or `isSelected`. Setting a new set removes exactly the attributes the previous one drew. The properties are kept and drawn again when a view is placed or its element is re-resolved. The traits Apple has and this surface does not publish are those with no ARIA equivalent worth drawing: `image`, `searchField`, `playsSound`, `keyboardKey`, `staticText`, `summaryElement`, `updatesFrequently`, `startsMediaSession`, `adjustable`, `allowsDirectInteraction`, `causesPageTurn`, `tabBar`, `toggleButton` and `supportsZoom`; and `accessibilityValue` is `aria-valuetext` only, which a role without a value ignores.


## Table views

A table view works the way it does on iOS: register a cell class for a reuse identifier, dequeue it in the data source, configure its outlets. The cell's row html lives in the `.xib` of the same name as the cell class.

```
src/uicomponents/transfers/
    transferCell.js      export class TransferCell extends UITableViewCell { @IBOutlet("#title", UILabel) titleLabel }
    transferCell.xib     <tr><td id="title"></td></tr>
```

```js
this.tableView.register(TransferCell, {forCellReuseIdentifier: "transfer"})
this.tableView.dataSource = this

tableViewNumberOfRowsInSection(tableView, section) {
    return this.transfers.length
}

tableViewCellForRowAtIndexPath(tableView, indexPath) {
    var cell = tableView.dequeueReusableCell({withIdentifier: "transfer", for: indexPath})
    cell.titleLabel.text = this.transfers[indexPath.row].name
    return cell
}
```

`selectRow({at, animated, scrollPosition})`, `deselectRow({at, animated})`, `indexPathForSelectedRow`, `indexPathsForSelectedRows`, `allowsMultipleSelection`, `setEditing(true, {animated})` and `cellForRow({at})` behave as on iOS; `scrollPosition` is a `UITableViewScrollPosition` (`none`, `top`, `middle`, `bottom`, also spelled `UITableView.ScrollPosition.top`) and scrolls the row to that edge or the middle, and `at: null` clears the selection as Apple's `nil` does. `dequeueReusableCell` always gives a row an instance of the class registered for the identifier it asks for, with that class's nib: when the row's previous cell was of another class (or another identifier) with a different nib it is disposed, which releases its outlets, targets and observers, and its element is replaced in place, so the rows keep their order, and `prepareForReuse()` is not sent to it; a class with the same nib takes the element over, so when two cell classes share one nib the row element is reused and each class must set every state it draws in its own configure step (`model` and the like), never counting on what the other class left on the element. A reload dequeues once per row. It hands back the cell object already bound to that row for the identifier, after sending it `prepareForReuse()`, and `reloadData` releases the cells a pass no longer uses, so a table reloaded on every filter holds one cell per row. A click on a `UIControl` in a cell (a `UIButton`, `UISwitch`, `UITextField`, or an element inside one, such as a button's icon) does not select the row, as on iOS a control handles its own touch: its action fires and `tableViewDidSelectRowAtIndexPath` does not. A click anywhere else in the cell selects the row: with `allowsMultipleSelection = false` it selects it, as Apple's tap does, so the row carries the `selected` class the framework draws (which the site's stylesheet decides whether to show), the row that was selected before receives `tableViewDidDeselectRowAtIndexPath`, then the tapped row receives `tableViewDidSelectRowAtIndexPath`; a tap on the row already selected sends `tableViewDidSelectRowAtIndexPath` again and deselects nothing, and `indexPathForSelectedRow` is the tapped row. A list whose tap navigates and must not look selected styles nothing for `.selected`, or sets `allowsSelection = false` and handles the tap itself. With `allowsMultipleSelection = true` a tap toggles, as on Apple: an unselected row is selected and `tableViewDidSelectRowAtIndexPath` is called, a selected one is deselected and `tableViewDidDeselectRowAtIndexPath` is called, through `selectRow` and `deselectRow` and the same path the selection checkbox takes, so a tap and a tick agree and the checkbox follows; a tap inside a nested control still does nothing. Programmatic `selectRow` and `deselectRow` call no delegate method. A page that wants "the checkbox ticks, a tap navigates" keeps `allowsMultipleSelection` off and wires its own checkbox as a control in the cell. The delegate, a `UIScrollViewDelegate` too, receives `scrollViewDidScroll(scrollView)` with the table as the scroll view, `tableViewDidSelectRowAtIndexPath`, `tableViewDidDeselectRowAtIndexPath` and, in editing mode, `tableViewCommitEditingStyleForRowAtIndexPath(tableView, editingStyle, indexPath)`, where `editingStyle` is a `UITableViewCellEditingStyle` (`none`, `delete`, `insert`, also spelled `UITableViewCell.EditingStyle.delete`). `UICollectionView` follows the same shape with `IndexPath` sections and items: a cell class registered with `register(cellClass, {forCellWithReuseIdentifier})` is instantiated by `dequeueReusableCell({withReuseIdentifier, for})` over the item's element, its outlets bound before `awakeFromNib`, and `reloadData` hands the same cell back for the same item, of the same identifier and class, after `prepareForReuse()`, with its element and handlers intact, so what `awakeFromNib` wired stays wired; a cell the new pass does not claim is disposed and its element removed. An identifier registered with a nib string still only supplies the html, and its cell is the plain `UICollectionViewCell`.

## Controls

- `UIControl`: `isEnabled = false` blocks the pointer and sets the `disabled` attribute, and a disabled control runs no action: neither its `addTarget` pairs nor an `@IBAction` bound to it fire on a click, `element.click()` or the keyboard, as a control that receives no touches on Apple, while `sendActions({for})` is a direct call, as Apple's `sendActions(for:)` is, and fires on a disabled control (it runs the connected actions directly, with no DOM event, so a submit, a checkbox toggle, a focus change and every handler above the control are left alone). `isEnabled` reads the element's own `disabled` attribute, since an outlet and an `@IBAction`'s sender are two views over one element and either may be the one that disabled it. So a static `disabled` attribute in a xib makes the control start disabled, as it does in HTML: its `isEnabled` is `false` and it runs no action until something enables it. Only a `UIControl` sender is gated: a plain `UIView`'s `@IBAction`, and a `UIKeyCommand` action such as Return, are not control actions and run as before. `@IBAction` cancels the click's default so an anchor does not navigate and a button does not submit a form, **except when the clicked element is a native checkbox or radio input**: cancelling it would undo the toggle, so the action sees the new `checked` state and the box stays as clicked (the exception follows the clicked element, not the sender's class). An `@IBAction` on a control is connected to the event Interface Builder connects by default for its class: `touchUpInside` for a `UIControl` or `UIButton`, `valueChanged` for `UISwitch`, `UISegmentedControl`, `UIColorWell` and `UIDatePicker`, `editingDidEnd` for `UITextField` and `UISearchTextField`; a color well's chooser opening is a click, so it runs nothing. Its sender is the outlet that owns the element when that outlet is an instance of the declared class, as Apple's sender is the outlet object, and a sender built over the element otherwise. A control's `addTarget` pairs and the `@IBAction` connections of a nib run in the order they were made, through one handler per element and event, and the two keep their own DOM policies: an `addTarget` pair stops its event at the control and an `@IBAction` does not, but cancels a click's default. The app's own `isEnabled` guards stay valid: they also run from Return and notification paths that are not control actions. `isSelected` is the `selected` class; `isHighlighted` is the `highlighted` class, set while the pointer is down on the control, for a control bound to an element and for one created in code and placed with `addSubview`. All three are there for stylesheets to draw. `state` returns the active cases of `UIControlState` (`normal`, `highlighted`, `disabled`, `selected`, `focused`); Apple's is an option set, which JavaScript lacks, so here it is a frozen array, `[UIControlState.normal]` for a plain control, following the `UIView.AnimationOptions` precedent. `addTarget(target, {action, for})` accumulates, as on iOS: a second pair never removes the first, nor an `@IBAction` bound to the same element, and the action runs on its target, `this`, with the sending control as its only argument, `(sender)` as Apple's does, and its return value is ignored; `removeTarget(target, {action, for})` removes one pair, or every action that target registered for the event when `action` is omitted, and the target's `@IBAction` connections to the control for that event with it. An `@IBAction` matched by class gives an id-less element `<owner id>-<action name>-<n>`, so the sender it hands over stays addressable. A target added before the control is placed (a `UIControl` created in code has no element until `addSubview` or `insertSubview` gives it one) fires once after placement, and again once after `removeFromSuperview` and a second placement; `removeTarget` after either removes it. A view that was never in the page keeps the element it was given, and is looked up again by its selector only once that element has been in the page and left it.
- `UIImage({data})` is Apple's `init?(data:)`: the image in the bytes of a `Uint8Array` or an `ArrayBuffer` (a view's offset is respected, a Node `Buffer` reads as its bytes), as `PDFDocument({data})` takes them. The format is what the leading bytes say, not what a caller claims: PNG, JPEG, GIF or WebP. Anything else, SVG included, an empty buffer, a string, a url or an array throws a `TypeError` naming `UIImage(data:)`, because Apple's init returns nil and a constructor cannot. It builds a `data:<mime>;base64,...` url, encoded in chunks (a 2 MB image is fine), so `UIImageView.image` draws it like any url, no object URL is made and there is nothing to revoke. A `UIImage` takes exactly one of `named`, `systemName` and `data`.
- `UIImageView`: `image` is the source of an `<img>`, `<video>` or `<lottie-player>` and the CSS background of any other element. `UIImage({systemName})` is an icon font symbol: its classes replace the previous symbol's on the element.
- `userActivity`: a view whose `NSUserActivity` has a `webpageURL` is a link to that page, so the url is written as the element's `href`. `webpageURL` is `URL?` as Apple's: it accepts a relative, http(s), `mailto:` or `tel:` url, as a string or a `URL`, returns what was set, and refuses anything else with a `TypeError` at the setter, since the value becomes an `href`; a `mailto:` or `tel:` activity on a pushed controller leaves the address alone, as any foreign origin does. Set it where iOS would open a page on tap, and keep the `<a>` in the nib. Read on a view bound to an anchor that already has an href, it is that page as a browsing activity, so an `@IBAction` sender can navigate with `sender.userActivity.webpageURL`.
- `UIScrollView`: `contentOffset`, `contentSize` and `setContentOffset(point, {animated})` read and move the element's scroll position; `animated: true` scrolls smoothly. `delegate` receives `scrollViewDidScroll(scrollView)` after every scroll of the element, however it was moved; the listener is released when the controller is dismissed, like the text field's delegate observers, and a delegate without the method observes nothing. A delegate set before the view has an element, a scroll view made in code and placed with `addSubview` later, is observed once it is placed. On the page's own scroller (`new UIScrollView("html")` or `"body"`) the delegate follows the document, because `scroll` does not bubble and the root scroller fires it at the document alone; reassigning the delegate, setting it to `null` or dismissing the controller removes that document listener. `isScrollEnabled` is a `Bool` that reads and writes. It reads the element's computed `overflow-x` and `overflow-y` live and is true when either is `auto` or `scroll`, so a media query's change is seen; `html` and `body` read true while their overflow is `visible`, because the viewport scrolls them. Setting `false` draws an inline `overflow-x` and `overflow-y` of `hidden`; setting `true` removes them, so the stylesheet's overflow returns, and a stylesheet that hides the element still reads `false` after it. Anything but a `Bool` throws a `TypeError`.
- Key commands: an `@IBAction` on a single character with no modifiers is typed into a focused text input instead of firing, as a `UIKeyCommand` is consumed by a first responder text field on iOS. Modified commands and non-character keys still fire, except the delete keys: both are consumed by a focused text input too, as a `UIKeyCommand` on Delete or Backspace is by a first responder text field in UIKit. `UIKeyCommand.inputDelete` is the forward Delete key, as Apple's is, and Backspace, which Apple names no constant for, is the input `"\u{8}"`: `UIKeyCommand.input("\b")`. Before this change `inputDelete` meant Backspace, so a caller that wanted Backspace writes `UIKeyCommand.input("\b")` now; `UIKeyCommand.input("Backspace")` still names the same key. `UIKeyCommand.wantsPriorityOverSystemBehavior`, a flag written before the input like a modifier (`UIKeyCommand.wantsPriorityOverSystemBehavior + UIKeyCommand.input("\b")`), lets one command run from a text input, and only such a command prevents the key's own behaviour, and only when its method does not return `false`, so a method can decline (for Backspace, when there is text to delete) and leave the editing to the field. `UIKeyModifierFlags.command` fires on Command on macOS and iPadOS and on Control on Windows and Linux, where there is no Command key and ⊞/Super is taken by the OS, so `.command + "f"` is Cmd+F on a Mac and Ctrl+F elsewhere and never fires on ⊞+F; `.control` is unchanged everywhere, and `.command + .control` is unreachable off-Apple; a control that declares `.command` and `.control` for one chord is dispatched once there, to the `.control` method. Mind the word-editing chords: inside a text input Ctrl+Arrow and Ctrl+Backspace jump and delete by word off-Apple, while Cmd+Arrow moves by line on a Mac, so a future `.command` binding on an arrow would steal word-jump from the text field.
- `UILabel`: `adjustsFontSizeToFitWidth` shrinks the font on one line until the text fits, no further than `minimumScaleFactor`; `textColor` takes a `UIColor`, or `null`, Apple's nil, which removes the inline colour so the stylesheet's returns (`undefined` still throws). It never reads back `null`, as Apple's is never nil: a colour set from code reads as it was written, and a label with no inline colour reads the computed colour, the one the page draws it in, as a `UIColor`.
- `UIButton`: `setTitle(title, {for: state})` keeps a title per state and draws the current state's, redrawn as `isEnabled` and `isSelected` change; `title({for: state})` and `currentTitle` fall back to the `.normal` title when none was set for the state, as Apple's do, and for a button nobody titled, to the text of its markup (`title({for})` answers `null` when there is none), as a nib's title is. A configuration assigned from another button's own carries that button's title. `setTitleColor(color, {for: state})` and `titleColor({for: state})`. A subclass may declare its own `title` property, as a Swift subclass may beside `title(for:)`; JavaScript then shadows `title(for:)` on that subclass, which the framework's own drawing does not depend on. More generally, an instance field named after one of its superclass's members makes that member unreachable on the subclass — on a control the names that matter are `title`, `text`, `image`, `state`, `isEnabled`, `isSelected`, `isHighlighted` and `delegate`. `setTitle(_:for:)`, `title(for:)`, `setTitleColor(_:for:)` and `titleColor(for:)` require the state, as Apple does; so do `sendActions(for:)`, `removeTarget(_:action:for:)`, `UIPickerView.numberOfRows(inComponent:)` and `selectedRow(inComponent:)`, and `UITableView.numberOfRows(inSection:)`. A call that omits the label throws a `TypeError` naming the method and Apple's signature — Swift refuses this at compile time and the nearest honest equivalent here is to refuse at the call. Before 1.6.0 the state defaulted to `.normal`; `setTitle("Save")` is now `setTitle("Save", {for: UIControlState.normal})`. The same holds for `setOn(_:animated:)`, `setProgress(_:animated:)`, `setEditing(_:animated:)`, `setDate(_:animated:)`, `setContentOffset(_:animated:)`, `UIPickerView.selectRow(_:inComponent:animated:)`, `UITableView.selectRow(at:animated:scrollPosition:)` and `deselectRow(at:animated:)`, `UISearchTextField.insertToken(_:at:)` and `UIView.insertSubview(_:at:)`: every label is required. Of these, `setProgress` animates the bar and `setContentOffset` scrolls smoothly when `animated` is true; `setOn`, `setEditing`, `setDate`, `UIPickerView.selectRow`, `UITableView.selectRow` and `deselectRow` record `animated` and do not act on it.
- `viewWillTransition({to: size, with: coordinator})` runs on the root controller and its children when the window changes size, and every view bound to them gets `layoutSubviews()`, so a layout that depends on width is redone there; `UIScreen.main.bounds` reads the viewport.
- Size classes: `view.traitCollection` and `controller.traitCollection` are a `UITraitCollection` with `horizontalSizeClass` and `verticalSizeClass`, each a `UIUserInterfaceSizeClass` (`compact`, `regular`, `unspecified`). When a resize changes them, the root controller and its children get `willTransition({to: newCollection, with: coordinator})` before the change, then `viewWillTransition`, then `traitCollectionDidChange(previousTraitCollection)` on the controllers and on every view, then `layoutSubviews()`; a resize that leaves the classes alone sends no trait hook. The mapping is this framework's, not an Apple threshold: horizontally `compact` below 768 CSS pixels of viewport width and `regular` from 768 up, vertically `compact` below 500 and `regular` from 500 up; Apple's classes come from the device and its orientation. Apple also sends `traitCollectionDidChange(nil)` when a view first joins the hierarchy, which this package does not yet. The classic pair is shipped on purpose, although iOS 17 deprecates it for `registerForTraitChanges(_:handler:)`, because it matches this framework's level. It is for code that must branch; responsive layout stays in the stylesheet.
- `UITraitCollection.current` is the page's collection, with its size classes. **It has no interface style yet**: there is no `userInterfaceStyle` and no `UIUserInterfaceStyle`. Apple's is light or dark, and a page can only guess that, from the brightness of a background or from `prefers-color-scheme`, neither of which is what the app's theme says (a workspace theme here is custom properties written on the root, and the browser's color scheme can disagree with it). So do not infer a style from `prefers-color-scheme`, or from a computed color, in app code either. The route for later is Apple's own: the app's theme code sets an explicit `overrideUserInterfaceStyle`, and the framework then sends `traitCollectionDidChange` when it changes. Until then `traitCollectionDidChange` is sent for size classes alone, and code that draws with resolved colors re-resolves where it applies a theme.
- `UIHoverGestureRecognizer`: added with `view.addGestureRecognizer`, its action runs with `state` `.began`, `.changed` and `.ended` as a mouse pointer enters, moves over and leaves the view; touches are not hovers, as on iPadOS. Recognizers expose `UIGestureRecognizer.State`.
- `UIColor`: `UIColor({named: "title-color"})` resolves the stylesheet's `--title-color` token, the way `UIColor(named:)` reads the asset catalog; `UIColor({red, green, blue, alpha})`, `UIColor({white, alpha})`, `UIColor.clear`, `.white` and `.black`. `cgColor` is the value a stylesheet understands, and it is what stands for Apple's `CGColor` here: `CALayer.borderColor` takes and returns it, a string such as `rgb(255, 0, 0)` or `var(--border-primary-default)`.
- `UIColor.resolvedColor({with: traitCollection})` (Apple's `resolvedColor(with:)`): a canvas, such as Chart.js, cannot read `var(--token)`, so `new UIColor({named: "chart-blue"}).resolvedColor({with: UITraitCollection.current})` is a new `UIColor` whose `cgColor` is the root element's computed value of `--chart-blue` (`#0070E0`, `rgb(...)`), read with one `getComputedStyle` call per resolve. A token defined as another token resolves through the chain (`--brand: var(--chart-blue)`), and a `var()` inside a larger value, such as `rgb(var(--channel))`, is replaced where it stands. A color that is no token (components, white, hex, `clear`) is concrete already and comes back as it is. A token that resolves to nothing throws a `TypeError` naming it, as `UIColor(named:)` fails for a name the asset catalog lacks, and a chain ending in a missing token names the missing one; a chain that loops, and a `var()` with a fallback (`var(--x, #fff)`), which this does not read, throw as well, so the result is never an unresolved `var(--x)` and a token missing from a theme is seen, never painted with a guess. The `with` label is required and must be a `UITraitCollection`; a page has one set of custom properties, so the collection does not choose a variant, it only says whose traits are meant. **Resolve at load, and again when the theme changes: never inside a Chart.js callback or per frame.** A theme here is custom properties set on the root, which no event announces, so no trait hook fires when one changes: the code that applies a theme re-resolves what it drew. No `getRed`-style components are provided.
- `UIView.frame` and `bounds`, and `UIScreen.main.bounds` and `nativeBounds`, are `CGRect`s: `origin` (`CGPoint`), `size` (`CGSize`), `width`, `height`, `minX`, `minY`, `maxX`, `maxY`, `midX`, `midY`, `isEmpty`, `contains(point)`, `insetBy({dx, dy})`, `offsetBy({dx, dy})`, and `CGRect.zero`; as on Apple's there is no `x` or `y`. `frame` is read-only on purpose: the stylesheet owns geometry here, and a setter would fight it.
- `UIView.transform` is a `CGAffineTransform` (`identity`, `{scaleX, y}`, `{translationX, y}`, `{rotationAngle}`, `scaledBy`, `translatedBy`, `rotated`, `concatenating`, `inverted`), written as the element's CSS transform; inside `UIView.animate` the element transitions to it.
- `view.layer` is the same `CALayer` for the view's whole life, as Apple's, and resolves the view's own element on every use (so two views that share an id, or a view whose element was replaced, each reach their own); `new CALayer(selector)` on its own still resolves the selector.
- `UIView.backgroundColor` takes a `UIColor`, and `layer.borderColor` takes a `CGColor`, which here is the string `UIColor.cgColor` returns (`layer.borderColor = color.cgColor`), as Apple's `CALayer.borderColor` is a `CGColor?` and its `UIView.backgroundColor` a `UIColor?`. A `UIColor` given to `layer.borderColor` throws a `TypeError` that names Apple's signature. Both take `null`, Apple's nil: it removes the inline value so the stylesheet's returns, and both read back `null` while the view has no value of its own (`undefined` still throws). `backgroundColor` reads back a `UIColor`; `layer.borderColor` reads back the string, the element's own inline value, so a hex reads as the browser's normalised `rgb(...)` and a token as the `var()` it was written as.
- `layer.borderWidth` (`CALayer.borderWidth`, Apple's `CGFloat`, default 0): above 0 the element gets an inline `border-width` and `border-style: solid` (a width alone draws nothing where the stylesheet has no border); `0` and `null` remove both, so the stylesheet's border returns, the same rule as `borderColor`'s `nil`. The getter reads the inline width only, `0` when there is none, and the stylesheet's borders are never touched. A negative or non-finite width throws a `TypeError`. An error border is `layer.borderColor = color` with `layer.borderWidth = 1`, and `null` for both clears it.
- `CAGradientLayer`: `colors`, `locations`, `startPoint` and `endPoint` (`CGPoint`), drawn as a CSS linear-gradient in an element that fills the superlayer once `view.layer.addSublayer(layer)` adds it.
- `CADisplayLink({target, selector})`: a frame callback on `requestAnimationFrame`. It does not tick until `add({to: RunLoop.main, forMode: RunLoop.Mode.common})`; from then on, before every frame, it calls the selector (a function, or the name of a method of the target) on the target with the link as the argument, as Apple's `@objc func step(displayLink:)` receives it. `timestamp`, `targetTimestamp` and `duration` are seconds, as Apple's `CFTimeInterval`s: `duration` is the display's nominal refresh interval, as Apple's is: 1/60 until a frame has been measured, then the smallest of the last 12 frame deltas (the smallest so far while fewer than 12 exist, so the very first interval is the only evidence for one frame), which a stutter cannot raise (a late frame only lengthens a delta) and a display that changes its rate overtakes within those 12 frames; a frame with no time since the last is not counted. `targetTimestamp` is `timestamp + duration`, so it never overshoots after a stutter. `isPaused` stops the ticks without removing the link; `remove({from, forMode})` stops them when the last mode goes; adding twice ticks once per frame. `invalidate()` cancels the next frame for good and drops the target and the selector, so the link keeps nothing alive, and an invalidated link cannot be added again. A browser has one event loop and no run loop modes: `RunLoop.Mode.default` and `.common` are accepted and make no difference, and any other run loop or mode throws a `TypeError`. `preferredFramesPerSecond` and `preferredFrameRateRange` are omitted: `requestAnimationFrame` follows the display.
- `UIButton.configuration` (`UIButton.Configuration?`): `UIButton.Configuration.plain()`, `.filled()`, `.tinted()` and `.gray()` make a value with `title`, `image`, `showsActivityIndicator` and `imagePlacement`. A button starts with a plain configuration whose `title` is the title its markup holds, as Interface Builder's default "Plain" style does, and `button.configuration` reads that value: a write to it goes back to the button, so `button.configuration.showsActivityIndicator = true` behaves as Swift's `button.configuration?.showsActivityIndicator = true`. A configuration assigned with `button.configuration = ...` is copied, as a struct is, so later writes to the original do not reach the button, and `null` is Apple's nil: every drawing the configuration made goes. The `title` is the button's normal title, so `setTitle(_:for:)` and `configuration.title` always agree. The four factories return the same value, because what a plain, a filled, a tinted and a gray button look like is the stylesheet's. **The indicator** draws a spinner and nothing else: it neither hides the title nor touches `isEnabled`, as on Apple, so a button that must not be pressed twice is disabled by the app with `isEnabled = false`. While it shows the button carries an `activity-indicator` attribute, for the stylesheet to decide what the title does (starkbank-web hides it), and the spinner is an overlay, the `uibutton-activity-indicator` element, a direct child of the button that fills it and centres its icon with flex, the button becoming its containing block when it is not positioned already; the icon spins on its own, so the centring does not depend on a `transform` that Font Awesome's `fa-spin` animation would override. The title's nodes are never moved, so an outlet to one of them stays attached, and a title drawn while it shows keeps the spinner. Turning it on twice changes nothing. `UIButton.showsActivityIndicator`, which disabled the button, was removed in the major that added the configuration: writing or reading it throws a `TypeError` naming `button.configuration.showsActivityIndicator`. **The image** is drawn in a `uibutton-image` element beside the title, before it for `NSDirectionalRectEdge.leading` and `.top` (the default is `.leading`) and after it for `.trailing` and `.bottom`, with the placement as an `image-placement` attribute for the stylesheet to lay out; a `UIImage(systemName:)` is its icon classes and a `UIImage(named:)` or `UIImage(data:)` an `img`. `NSDirectionalRectEdge` has `top`, `leading`, `bottom` and `trailing`, with Apple's raw values, and no `all`.
- `UITextField.textContentType` (`UITextContentType?`): the cases this page can honour, each drawn as the input's `autocomplete` token through the setter alone: `.oneTimeCode` `one-time-code`, `.newPassword` `new-password`, `.password` `current-password`, `.username` `username`, `.emailAddress` `email`, `.telephoneNumber` `tel`, `.name` `name`, `.givenName` `given-name`, `.familyName` `family-name`, `.organizationName` `organization`, `.postalCode` `postal-code`, `.fullStreetAddress` `street-address`, `.addressCity` `address-level2`, `.addressState` `address-level1`, `.countryName` `country-name`, `.creditCardNumber` `cc-number` and `.URL` `url`. `null` removes the attribute, so the browser's default returns, and the getter reads back the case a token names (`null` for an `autocomplete` no case names, such as `off`). Anything outside the type, a raw token included, throws a `TypeError` with Apple's signature: there is no Apple case for `autocomplete="off"`, so a field that must not be autofilled has no property for it here. A `UISearchTextField` draws it on its inner input.
- `UITextField.textColor` (`UIColor?`, mirroring `UILabel.textColor`): a color is drawn as the input's inline `color` and `null` removes it, so the stylesheet's color returns; the getter reads the inline color only, never the computed one, so a field nobody colored reads `null`, and setting the same value twice is the same as once. The placeholder keeps its own color. A `UISearchTextField` applies it to its inner input, where the typed text is.
- `UITextField`: `placeholder` reads and writes the attribute; `isEditing` is true while the field, or a descendant such as a search field's input, has the focus. The delegate gets `textFieldShouldBeginEditing` and `textFieldDidBeginEditing` when the field takes the focus (an explicit `false` resigns it again, since the DOM cannot refuse a focus), `textFieldShouldEndEditing` and `textFieldDidEndEditing` when it loses it, `textFieldShouldReturn` on Return, `textFieldShouldChangeCharactersInRangeReplacementString(textField, range, string)` on `beforeinput` with the selection as an `NSRange` and the typed string (empty for a deletion), and `textFieldDidChangeSelection` on the document's `selectionchange` while the field is focused (observed through `NotificationCenter`, so it is released with the controller); `delegate = null` stops all of them; with a caret, the range of a deletion is what the key removes (the grapheme cluster before it for Backspace and after it for Delete, by `Intl.Segmenter`, or a surrogate pair or one unit where that is missing; up to the word boundary for a word deletion; up to the start or end of the line for a line deletion), a selection is the range as it stands, and a deletion that removes nothing, a Backspace at the start, does not ask the delegate; only an explicit `false` from a `should` method prevents the default, so a delegate that returns nothing proceeds. `textFieldShouldClear` and `textFieldDidEndEditing(_:reason:)` are not provided: the first has no reliable DOM event and the second's reason has one reachable case. Foundation gains `NSRange({location, length})` and the global `NSNotFound`. Editing does not end on a keystroke: to follow the text as it is typed, add a target for `UIControlEvent.editingChanged`. `isFirstResponder`, `becomeFirstResponder()`, `resignFirstResponder()`.
- `UITextField.pasteDelegate` (Apple's `UITextPasteDelegate`): `textPasteConfigurationSupportingTransformPasteItem(textField, item)` is called once for each paste, with one `UITextPasteItem`; the method was named `textPasteConfigurationSupportingTransform` before the major that renamed it, and a delegate that still has that name is refused when it is assigned, because it would never be called. Its `itemProvider` is an `NSItemProvider` holding, as strings, only the flavours the clipboard carries among `UTType.plainText`, `UTType.html` and `UTType.rtf` (`registeredTypeIdentifiers` lists them), and `loadDataRepresentation({forTypeIdentifier, completionHandler})` hands the UTF-8 bytes as a `Uint8Array`, a copy each time, or a null data and an `Error` for a type the paste does not hold. Decode them as text (`new TextDecoder().decode(data)`) and never parse them into the page. The item's result decides what the paste does: `setNoResult()` consumes it and inserts nothing, `setStringResult(string)` consumes it and, once the field's delegate agrees, inserts that string as text at the selection and fires `editingChanged` once; on an input whose type has no selection, such as `type="email"` or `number`, the string is appended at the end of the value instead, and `setDefaultResult()`, or no result, leaves the paste to the browser; the last one set wins, and only the paste's `preventDefault` follows from it. The framework binds the field's `paste` event only while a `pasteDelegate` is set, and removes it on reassignment, `null`, removal from the superview and disposal. **A deviation from Apple's:** a browser exposes the clipboard only while the paste event runs, so the delegate is called synchronously, the result must be set inside that call, and `loadDataRepresentation`'s completion handler runs before the call returns, where Apple's is asynchronous. **Each flavour is capped at 256 KiB of UTF-8**, cut at a code point, before the app sees it, so the app's own parsing has a bound to rely on; split on separators and skip an over-long token before running a backtracking pattern on it. The clipboard's `clipboardData`, its files and the event never reach the app and no file item is exposed: a paste carrying files alone does not call the delegate, and one carrying text and files shows only the text. A paste with none of the three flavours does not call it either. Nothing from the clipboard is logged. The framework cannot hide `window.event`, which a browser sets to the paste event for the length of the call, so keeping the event away from app code is the app's gate: starkbank-web's G3 forbids any `window.` access in app code. **The order of a paste:** the transform runs first, then the field's `delegate.textFieldShouldChangeCharactersInRangeReplacementString(textField, range, replacement)` is asked with the selection as the range and the string the paste will insert as the replacement, which is the transform's `setStringResult` string; only an explicit `false` cancels the insertion (the paste is still consumed, so the browser does not paste the clipboard's text instead), and `setNoResult()` asks nothing. A paste the transform leaves to the browser (`setDefaultResult()`, or no result) is asked by the browser's own `beforeinput`, which carries the clipboard's text and which the framework answers through the same method, so a digit or length rule on an amount field sees every paste, once. A mask applied on `editingChanged` still runs on an accepted string result, because the insertion fires it. The other `UITextPasteDelegate` methods are not provided.
- `UITextView` (a `UIScrollView`, as Apple's is, over the xib's `<textarea>`): `text` reads and writes the value, as text and never as markup, so `<b>x</b>` typed or set stays those characters; `delegate.textViewDidChange(textView)` follows every edit the user makes, on `input` and not on a key, and not a programmatic `text = ...`, as on Apple, and `scrollViewDidScroll` still reaches the same delegate. `isScrollEnabled` is read-write, as a scroll view's is, but on a text view it is about the view's own height rather than the element's overflow: `true`, the default, leaves the height to the stylesheet; `false` sizes the height to the content, so the view grows and shrinks with its text, and setting it back to `true` gives the height back to the stylesheet. Sizing is a fixed routine: the padding and border the height adds or drops is read from computed style once, in `awakeFromNib` (at the first fit for a view not in the page yet), and each edit then writes `height: 0px`, reads `scrollHeight` once and writes the measured height, a pinned height being what `scrollHeight` cannot report below and `height: auto` being a textarea's two rows; a repeated `text` or `input` with the text unchanged writes nothing. - `UIDatePicker`: `date` (in the default `.date` mode `date = null` clears the field, and `date` is `null` while it is empty), `minimumDate`, `maximumDate`, `locale`, `datePickerMode = UIDatePicker.Mode.yearAndMonth`. `datePickerMode` is a `UIDatePicker.Mode`, with Apple's raw values: `.time` 0, `.date` 1, `.dateAndTime` 2, `.countDownTimer` 3, `.yearAndMonth` 4; a string is refused with a `TypeError` naming `UIDatePicker.datePickerMode`, and so is `.countDownTimer`, which is Apple's case but has no control on a page. Since 1.9.0 `datePickerMode = UIDatePicker.Mode.time` is Apple's `.time`: it replaces the calendar with the ClockPicker 0.0.7 jQuery plugin over the same input, so the plugin's js and css must be on the page too, like jquery-ui. `date` then holds hours and minutes (the input reads and writes `HH:mm`; `date` is that time on the day last written, today until one was, `null` for text the clock cannot have written, and writing a date keeps its day for the date read back and its time for the clock), a close that changes the time is one `valueChanged` and one that leaves it sends none, `minimumDate` and `maximumDate` are ignored (the plugin has no limits) and read `null`, and switching back to `.date` removes the clock and rebuilds the calendar. ClockPicker's 12-hour mode is not supported. In `.yearAndMonth` `date` is the month that was picked or written, as the first of it at midnight local time, and never `nil` as Apple's is: entering the mode holds the first of the current month in memory without drawing it, so a nib's placeholder stays, and a caller that prefills the field must set `date` itself; `date = null` and `setDate(null, ...)` throw a `TypeError`. It is held by the picker, not read back from the widget's "MMMM yyyy" text. `datePickerMode = UIDatePicker.Mode.dateAndTime` is Apple's `.dateAndTime`: the same input becomes the browser's own `datetime-local` (no jquery-ui widget, no plugin), a click on it calls `showPicker()`, `date` is the day and time to the minute in local time (`null` for an empty or impossible value) and `minimumDate` and `maximumDate` are the input's `min` and `max` (set them after the mode, as a switch drops them). A change the user commits is a `valueChanged` through the input's own `change` event; writing `date` sends none. The browser's own language draws the field, so `locale` is kept but does not change it, and switching back to `"date"` restores the text input and rebuilds the calendar. **When valueChanged is sent:** only when a user's selection changed the date (the day in `.date`, the month in `.yearAndMonth`, the time in `.time`, the value in `.dateAndTime`), never for a pick that leaves it as it was and never for a write from code, and a disabled picker does not open its calendar and sends nothing for a user's change, while `sendActions(for:)` stays a direct call, as on every control. **`date` is still `nil`, on purpose:** Apple's `date` is never nil, but a web date input can be cleared by the user and the sites read an empty field as "no filter", and Apple's non-optional `date` has no state for that.
- `UIPasteboard.general`, since 1.9.0: `string` and `hasStrings`. ## Video

`import "AVKit"` brings AVFoundation's player, as it does in Swift. An `AVPlayer` plays one `AVPlayerItem`, which wraps an `AVURLAsset`; it draws through an `AVPlayerLayer`, which on the web is a `<video>` element. An `AVPlayerViewController` outlet bound to a `<video>` plays there, and bound to any other element appends the `<video>` it plays in.

```js
@IBOutlet("#hero-video", AVPlayerViewController) heroVideo

viewDidLoad() {
    this.heroVideo.player = new AVPlayer({url: "/static/hero.mp4"})
    this.heroVideo.videoGravity = AVLayerVideoGravity.resizeAspectFill
    NotificationCenter.default.addObserver(this, {name: AVPlayerItem.didPlayToEndTimeNotification, object: this.heroVideo.player.currentItem, selector: "videoDidEnd"})
}
```

`play()`, `pause()`, `rate`, `isMuted`, `volume`, `currentTime()`, `seek({to, completionHandler})`, `status`, `error`, `timeControlStatus`, `actionAtItemEnd` and `replaceCurrentItem({with})` follow AVFoundation. Times are Core Media `CMTime` values, as in Swift: `player.currentTime().seconds` reads one, `player.seek({to: new CMTime({seconds: 10, preferredTimescale: 600})})` makes one, and an item's `duration` is `CMTime.indefinite` until the media reports it. `import "AVKit"` brings `CMTime` along, the way AVFoundation re-exports Core Media. The player writes only what the app sets, so a `<video muted autoplay loop>` keeps its own attributes. `AVPlayerLayer({player})` makes a layer with its own element for `view.layer.addSublayer(layer)`.

## PDF

`import "PDFKit"` brings Apple's PDFKit, since 1.7.0. A `PDFView` outlet shows a `PDFDocument`; it builds its own `.pdfViewer` element inside whatever it is bound to, the way an `AVPlayerViewController` builds its own `<video>`.

```js
@IBOutlet("#pdf-preview", PDFView) pdfView

viewDidLoad() {
    this.pdfView.document = new PDFDocument({url: "/static/legal-privacy.pdf"})
    this.pdfView.backgroundColor = new UIColor({named: "border-color"})
    NotificationCenter.default.addObserver(this, {name: NSNotification.Name.PDFViewDocumentChanged, object: this.pdfView, selector: "documentDidChange"})
}
```

`currentPage` (read-only; `go({to: page})` is how it changes, as in PDFKit), `goToNextPage(sender)`, `goToPreviousPage(sender)`, `goToFirstPage(sender)` and `goToLastPage(sender)` with their `canGoToNextPage`, `canGoToPreviousPage`, `canGoToFirstPage` and `canGoToLastPage` (each `goTo…` is a no-op while its `canGoTo…` is false; the sender is Apple's target/action argument and is unused), `scaleFactor`, `minScaleFactor`, `maxScaleFactor`, `autoScales`, `displayMode` (a `PDFDisplayMode`), `displayDirection` (a `PDFDisplayDirection`, the scroll axis of the continuous modes), `displaysPageBreaks` (needs `pdf_viewer.css`, whose `.pdfViewer.removePageBorders` rules draw it), `visiblePages`, `currentSelection` (a `PDFSelection?`), `setCurrentSelection(selection, {animate})` (nil clears), `clearSelection()` and `highlightedSelections` (a `[PDFSelection]?`) follow PDFKit. Selection is always on — PDFKit has no switch for it, so there is none to expose. `visiblePages` is pull-based: it measures the page views against the view when read, and PDFKit publishes no `PDFViewVisiblePagesChanged`, which would have to measure at scroll rate.

`PDFDocument(data:)` is `new PDFDocument({data})` over a `Uint8Array` or an `ArrayBuffer` and nothing else: a string, a url or any other type throws a `TypeError`, so the scheme boundary below cannot be walked around by handing a `data:` url in as bytes, and a document takes a url or data, never both. pdf.js gets a copy of the bytes, since it transfers the buffer it is given and would otherwise detach the caller's; `documentURL` is `null` for such a document, as Apple's is `nil`. `PDFDocument(url:)` accepts a relative path, a protocol-relative `//host/…` url (the origin policy there belongs to the host's CSP `connect-src`, not this check) or an `http(s):` url, judged the way a browser itself resolves the string, not by reading it as written; `pageCount`, `page({at: index})`, `index({for: page})` (`NSNotFound` for a page of another document) and `documentURL` read it, `page({at:})` 0-based like Apple's own `PDFPage` position. `new PDFPage()` has no document and no label, as Apple's; the pages a document hands out are the document's own and identical across calls. `new PDFSelection({document})` is empty, as Apple's is before it is extended, and stays empty here: `add`, `extend` and the rest of the building API are not backed by pdf.js.

Find is asynchronous, as pdf.js extracts text through a worker: `document.beginFindString(query, {withOptions: [NSString.CompareOptions.caseInsensitive]})` posts `NSNotification.Name.PDFDocumentDidBeginFind`, one `PDFDocumentDidFindMatch` per match with its `PDFSelection` in `userInfo[PDFDocumentFoundSelectionKey]`, and `PDFDocumentDidEndFind`, which carries no `userInfo`, once pdf.js has searched the whole document, which it does without rendering a single page's canvas. `isFinding` is true from the begin until the end, a `cancelFindString()` or the document leaving its view. Four `NSString.CompareOptions` are honoured: `.caseInsensitive`, `.diacriticInsensitive`, `.literal` (which wins over `.diacriticInsensitive`) and `.backwards`; Apple's default compare is case- and diacritic-sensitive, and so is this one. The other five cases do nothing here and are not exposed. `cancelFindString()` clears the field; a new `beginFindString` call supersedes whichever search is still running. A `PDFDocumentDelegate` assigned to `document.delegate` gets `didMatchString(selection)`, `documentDidBeginDocumentFind(notification)`, `documentDidFindMatch(notification)` and `documentDidEndDocumentFind(notification)`, each with exactly Apple's one argument and each optional.

PDFKit's notification names are `NSNotification.Name` constants, as Apple's are: `PDFViewDocumentChanged`, `PDFViewPageChanged`, `PDFViewScaleChanged`, `PDFViewSelectionChanged`, `PDFViewDisplayModeChanged`, `PDFDocumentDidBeginFind`, `PDFDocumentDidFindMatch` and `PDFDocumentDidEndFind`. They are published when `PDFKit` is imported, and only the ones PDFKit actually posts are, so an observer never waits for a name nothing can send. A name is a plain string and the notification observers receive is the plain `{name, object, userInfo}` `NotificationCenter` delivers, not an `NSNotification`.

A `PDFViewDelegate` assigned to `pdfView.delegate` may implement `pdfViewWillClickOnLinkWithURL(pdfView, url)`. Implementing it means PDFKit does not open the link: the delegate receives a WHATWG `URL`, already limited to `http(s):` by PDFKit (internal `#` destinations and other schemes never reach it), and opening it is the delegate's job. A delegate that opens it should pass `noopener` itself, since PDFKit's own `target="_blank"` with `rel="noopener noreferrer nofollow"` no longer apply once the delegate takes over. Without the method, links behave as before.

Limitations, all deliberate. `beginFindString` requires the document to already be set on a `PDFView`; Apple's own `PDFDocument` can search a document no view is showing, PDFKit's cannot, because the search is driven by the view's `EventBus` and `PDFFindController`. `highlightedSelections` only reports what pdf.js's own find just produced — assigning it a selection list of your own choosing has no effect beyond bookkeeping, since pdf.js has no API to highlight an arbitrary selection outside of a find. Setting it to `[]` or `nil` does clear what is on screen, the one direction pdf.js supports. There is no synchronous `findString(_:withOptions:)` and no `PDFPage.string` or `PDFDocument.string`, because pdf.js extracts text through a worker and only the asynchronous find can be honest about that. There is no display box (`PDFDisplayBox`, `bounds(for:)`): pdf.js exposes one crop-intersected-media view box, not Apple's separate boxes. Nothing here is Apple's `PDFThumbnailView`, `PDFAnnotation`, `PDFOutline`, `PDFDestination` or `PDFAction` either.

Since 1.8.0 PDFKit bundles pdf.js, so the app installs nothing and sets nothing: a `PDFView` outlet and `new PDFDocument({url})` are the whole contract, with no globals to publish, no worker url and no stylesheet to wire. Importing PDFKit needs a browser: in bare Node the import itself throws `document is not defined` from pdf.js's viewer, naming pdf.js and not this package, so server-side or type-extraction tooling must not import it. The worker is a webpack chunk emitted beside the consumer's bundle, so there is no url to serve and no copy step. `pdfjs-dist` is a pinned dependency of this package: a bundle that imports `PDFKit` pays about 1.9 MB for it (772 KB of main code plus a 1.1 MB worker chunk, minified) and a bundle that does not pays nothing, which the import-graph guard in `test/frameworks.test.js` asserts. `pdfjs-dist` brings `@napi-rs/canvas` as an optional dependency, so installing cocoatouch installs a native binary for the platform; it is pdf.js's Node-side canvas backend, never reached in a browser, and costs zero bundle bytes. Two requirements fall on the consumer: the server must serve webpack's emitted chunks from the build directory at `output.publicPath`, and a site whose stylus rule covers `node_modules` must exclude `pdfjs-dist` before importing PDFKit.

PDFKit's stylesheet is scoped. pdfjs-dist's own `pdf_viewer.css` styles unscoped names (`.sidebar`, `.page`, `.dialog`, `.toggle-button`) and `:root`, which restyled the host app of every page that imported PDFKit, whether or not a PDF was on it. PDFKit no longer imports it: it imports `styles/pdf_viewer.scoped.css`, generated from the installed pdfjs-dist by `npm run styles:pdfviewer` (`scripts/scopePdfViewerCss.mjs`, with postcss as a devDependency only) so that every selector is a descendant of `.ct-pdfview`, the class a `PDFView` adds to its element when it binds. pdf.js's `:root` blocks, `color-scheme: light dark` among them, become that element's own, except the variable pdf.js sets on the document from script; `html`, `body` and print-only selectors are dropped; relative `url()`s become `pdfjs-dist/web/images/...` module paths, which is why `pdfjs-dist` is a dependency and not a devDependency. A drift test fails when the committed file is not what the generator makes from the installed pdfjs-dist, so a pdfjs-dist bump regenerates it. Nothing of pdf.js's outside a `PDFView` is styled, so the editor and comment widgets pdf.js appends to `body` are unstyled here; PDFKit's read-only view uses none. The framework's own `:root { color-scheme: normal }` reset is gone, as the leak it fixed is.

Three globals are the only way to set paths `PDFDocument(url:)` has no parameter for, because Apple's has none either: `pdfjsCMapUrl` and `pdfjsStandardFontDataUrl` for correct glyph metrics on a non-Latin script, and `pdfjsWasmUrl` for pdf.js's wasm image codecs, which also needs `'wasm-unsafe-eval'` added to the host's `script-src` — a CSP change this package does not make for you. All three are read the same way, at call time, and simply omitted when unset.

pdf.js's own `PDFViewer` enforces two things about the element `PDFView` is bound to that are worth knowing before styling it: it must be a `<div>` (not any other tag), and once it is actually on screen (has an `offsetParent`) its computed `position` must be `absolute`, or the real pdf.js throws `"The container must be absolutely positioned."` straight out of its constructor. A host's stylesheet needs to give that element a definite size another way — `inset: 0` inside a `position: relative` wrapper of a fixed or viewport-relative height is the usual shape — rather than `position: relative` on the bound element itself.

## Delegates

A delegate or data-source method is the Objective-C selector with the colons removed and each following piece capitalised, and its arguments are positional in Apple's order, the sender first: `tableView(_:numberOfRowsInSection:)` is `tableViewNumberOfRowsInSection(tableView, section)`, `textField(_:shouldChangeCharactersIn:replacementString:)` is `textFieldShouldChangeCharactersInRangeReplacementString(textField, range, string)`. This is the one exception to labels-as-object-keys. Optional methods are optional: absence is never an error, and the framework supplies Apple's default (one section, a blank picker row). A `Bool` return is honoured only when it is exactly `false`; `undefined`, `null` and anything else mean "proceed". Five names predated the convention and were renamed in 1.6.0: `tableViewCommitEditingStyleForRowAt` → `tableViewCommitEditingStyleForRowAtIndexPath`, `collectionViewDidSelectItemAt` → `collectionViewDidSelectItemAtIndexPath`, `numberOfItemsInSection` → `collectionViewNumberOfItemsInSection`, `pickerViewTitleForRow` → `pickerViewTitleForRowForComponent` and `pickerViewDidSelectRow` → `pickerViewDidSelectRowInComponent`. Because an optional method under a retired name would simply never be called, assigning a `delegate` or `dataSource` that still carries one throws a `TypeError` naming the replacement. That check is a migration diagnostic at the framework's boundary, not a UIKit behaviour, and it is removed in the next major. The argument order is Apple's; where Apple's own signature carries no sender — `PDFDocumentDelegate`'s four find methods — none is passed.

## Notifications

`NotificationCenter.default` is observer keyed, and one object for the page: it is held on the global object, so a page that loads two copies of the package has one center, and an observer added through one copy hears what the other posts. Pass a DOM event target as `object` to observe that event; leave it out to post and observe in-app notifications.

```js
NotificationCenter.default.addObserver(this, {name: "scroll", object: window, selector: () => this.updateMenu()})
NotificationCenter.default.addObserver(this, {name: "cartDidChange", selector: "cartDidChange"})
NotificationCenter.default.post({name: "cartDidChange", userInfo: {count: 3}})
NotificationCenter.default.removeObserver(this)
```

Everything a view or controller observes is released when its root controller is dismissed, so window and document listeners never pile up across navigations. Keyboard `@IBAction`s register the same way.

## Bundling

The nib link is an ordinary module import, `import { CardView } from "./cardView.js"; CardView.nib = "…"`, so it survives Terser's defaults: the class identifier is mangled and the binding is mangled with it, and nothing is looked up by name. `keep_classnames` and `keep_fnames` are not needed, and nothing should start depending on them. `mangle.properties` would break it, since `nib`, `iboutlets`, `ibactions`, `ibinspectables` and the generated ids are property names. A package that ships `.xib` files must list them in its `sideEffects`, `"./src/**/*.xib"`, as `starkbank-webkit` does, or tree shaking drops the nib assignments; this package has no `sideEffects` key, which is the safe default. A page module reached through a dynamic `import()` carries its nibs into that chunk, so code splitting works per page. PDFKit is not re-exported from the root entry, `"cocoatouch"`, because pdf.js is 35 MB installed and about 1.9 MB bundled (772 KB of main code and a 1.1 MB worker chunk, minified), and only a bundle importing `PDFKit` should pay for that.

## Editor and linter support

The ambient names are declared, so an editor can still jump to `UIViewController`, complete its members and underline a typo before the build does. The package ships generated `.d.ts` files for every entry plus `types/globals.d.ts` for the names `import "UIKit"` makes ambient. In a JavaScript project, point `jsconfig.json` at them once:

```json
{
    "compilerOptions": {
        "checkJs": true,
        "experimentalDecorators": true,
        "paths": {
            "UIKit": ["./node_modules/cocoatouch/types/UIKit.d.ts"],
            "Foundation": ["./node_modules/cocoatouch/types/Foundation.d.ts"]
        }
    },
    "files": ["node_modules/cocoatouch/types/globals.d.ts"],
    "include": ["src"]
}
```

For ESLint, `cocoatouch/eslint/globals` exports the same names as a `globals` object, so `no-undef` accepts them and still flags misspellings.

**Reading a signature.** A labelled argument appears in the declaration as the object key Apple gives it, so `setTitle(title, {for: state}?: {for: "normal" | …})` is Apple's `setTitle(_:for:)`. A label without `?` is one Apple requires: omitting it throws a `TypeError` naming the method and the Swift signature. A label with `?` is one Apple makes optional, and keeps Apple's default — `removeTarget`'s `action?` defaults to none, as `Selector?` does. The object itself is marked optional because JavaScript lets you leave an argument out; the labels inside it are what Apple requires, and leaving the object out throws exactly as leaving a label out does. The type in a declaration is enforced, not decorative: a member refuses a value of the wrong type with a `TypeError` naming the method, the Swift signature, the expected type and what it received, because Swift would have refused it at compile time. `null` is accepted only where Apple's type is optional. Value types — `CGPoint`, `CGSize`, `CGRect`, `IndexPath`, `NSRange` — are checked by shape, as Swift checks structs structurally; reference types such as `UIColor` are checked with `instanceof`, which a second installed copy of the package (two `node_modules/cocoatouch`, or a symlinked checkout beside a registry install) would fail for a correct value, so keep one copy.

## Server side rendering

Capture the `<cocoatouch>` inner html after `present`, serve it with `window.__PRERENDERED = true`, and call `controller.restore(controller)` instead of `present`. Outlets and actions rebind to the existing DOM, and views added at runtime through `addSubview` are found again by their `@IBAction` selectors. `restore(_:)` is this framework's hydration entry point, not a UIKit interface; UIKit's vocabulary for it is state restoration, which is where this is headed.

One element has one owner. The owner is recorded as each view is bound, and from then on it supersedes the selector-equality rule that follows: an `@IBAction` that reaches an element a bound view owns, by whatever selector, awakes no second view over it. A registered view class is revived only for an action target no bound responder already answers with that same selector, so an outlet that declares `@IBAction("#logo")` is not shadowed by a page-wide ghost of its own class; a target inside an outlet container that declares no action on it, such as a message view added into `this.messagesView`, is still revived. When a class and its subclass both match the same target, only the most derived is revived. Two limitations remain. Sibling subclasses that declare the same action selectors cannot be told apart by this scan; the fix is `restorationIdentifier`, which is not here yet. And a revived view is constructed with no selector, so its class fields and `init()` run, but `init()` runs against an empty `$el`: work `init()` does on the element, such as `UISearchTextField` appending its input, does not land. A view that touches its element should do so in `awakeFromNib`, which `restore` does not send either; `didMoveToWindow` is the hook a restored view receives.

### UniformTypeIdentifiers

`import "UniformTypeIdentifiers"` brings `UTType`, only what a file picker and a drop zone name. The constants are `UTType.pdf`, `.image`, `.png`, `.jpeg`, `.commaSeparatedText`, `.plainText`, `.html`, `.rtf`, `.gif`, `.webP`, `.bmp`, `.heic`, `.heif`, `.tiff`, `.svg`, `.item` and `.folder`, each with Apple's `identifier` (`com.adobe.pdf`, `public.image`, ...), `preferredFilenameExtension` and `preferredMIMEType` (`null` where a browser has none, as for `image`), and `conforms({to})` follows Apple's hierarchy: `png` and `jpeg` conform to `image`, everything to `item`, `folder` to neither `image` nor `pdf`. The parents are the ones the system declares: `pdf`, `image` and `text` (and so the Office types, `.spreadsheet`, `.html`, `.rtf` and the rest under them) conform to `public.content` and `public.data` as well as `public.item`, while `.archive` is data and no content and `.folder` is an item and no data. `new UTType({filenameExtension: "pem"})` finds a known type (`jpg` is `public.jpeg`, whose preferred extension is `jpeg`) and makes a dynamic one, `dyn.pem`, for an extension nobody declared, as Apple's does. `new UTType({mimeType})` finds a known type and makes a dynamic one, `dyn.<mime>` with that MIME type as its `preferredMIMEType` (and as its `accept` token in a picker), for a well-formed `type/subtype` nobody declared. Apple's initializers return nil for a value that is not shaped like one, which `new` cannot, so an empty string or a MIME type without a subtype throws a `TypeError`. Exactly one label is taken. `.plainText`, `.html` and `.rtf` (`public.plain-text`, `public.html`, `public.rtf`) are the three flavours of a paste: each has its MIME type (`text/plain`, `text/html`, `text/rtf`) and Apple's preferred filename extension (`txt`, `html`, `rtf`), and a file name finds them: `new UTType({filenameExtension: "txt"})` is `public.plain-text` and its `preferredMIMEType` is `text/plain` (`htm` is `public.html`), where it was a dynamic type with no MIME type before this version, so an app that maps a file name to a MIME type now gets `text/plain`, `text/html` or `text/rtf` for these three. The image constants `.gif` (`com.compuserve.gif`), `.webP` (`org.webmproject.webp`), `.bmp` (`com.microsoft.bmp`), `.heic` (`public.heic`), `.heif` (`public.heif`), `.tiff` (`public.tiff`, extensions `tiff` and `tif`) and `.svg` (`public.svg-image`) conform to `.image`, each with its extension and MIME type (`image/gif`, `image/webp`, `image/bmp`, `image/heic`, `image/heif`, `image/tiff`, `image/svg+xml`), and are found by extension and by MIME type; `heic` and `heif` sit under `public.heif-standard`, as Apple's do, and neither conforms to the other. Because `.svg` now conforms to `.image`, a check that an upload is an image no longer keeps an SVG out: an app that accepts only raster pictures decides that itself, as the content it sends, never from the type. AVIF has no named `UTType` constant on Apple, so there is none here, but the system declares `public.avif`, as this table does: `new UTType({filenameExtension: "avif"})` and `new UTType({mimeType: "image/avif"})` find it, its MIME type is `image/avif` and it conforms to `.image` (`avifs`, the sequence, stays dynamic). The Office, OpenDocument and archive types resolve by extension and by MIME type, with the conformance Apple reports: `doc` (`com.microsoft.word.doc`, `application/msword`), `docx` (`org.openxmlformats.wordprocessingml.document`, under `org.openxmlformats.openxml`), `odt` (`org.oasis-open.opendocument.text`), `xls` (`com.microsoft.excel.xls`, a `public.spreadsheet`), `xlsx` (`org.openxmlformats.spreadsheetml.sheet`, an openxml spreadsheet) and `zip` (`public.zip-archive`, a `public.archive`); a `docx` is **not** a zip as far as Apple's `UTType` says. Apple names no constant for the Word, OpenDocument and Excel types, so there is none here; `UTType.zip`, `UTType.archive` and `UTType.spreadsheet` are the constants Apple ships. An app that maps a file name to a MIME type through `new UTType({filenameExtension}).preferredMIMEType` now gets these types' own MIME types instead of nothing.

### FileManager

Foundation's `FileManager.default` reads what the user picked or dropped, and nothing else: a page has no file system, so a path here is the `file:` URL the framework minted for a `File` (`UIDocumentPickerViewController`, `UIDropInteraction`), `url.href`. `displayName({atPath})` is the original file name, `attributesOfItem({atPath})` is `{[FileAttributeKey.size]: bytes}` and throws when nothing is at the path, `contents({atPath})` is the bytes as a `Uint8Array` (Data, as in `PDFDocument({data})`), `contentsOfDirectory({at: url, includingPropertiesForKeys: null})` lists a dropped folder as an array of `file:` URLs, each registered as it is listed (resource keys are not supported, so the label takes `null`) and `removeItem({at: url})` releases the file. One answer differs from Apple's because a browser cannot read synchronously: `contents` and `contentsOfDirectory` return a Promise. A path the framework did not mint, whether another `file:` URL, `blob:`, `http:` or a relative one, has nothing at it, and no request is ever made. What each method does with a missing path, one the app released with `removeItem`, or a file the browser can no longer read. `attributesOfItem` and `contents` answer as Apple's do; the three rows marked as deviations do not, kept on purpose so that a path that is gone answers a plain value and cleaning it up never throws:

| Method | Missing or unreadable path |
|---|---|
| `displayName({atPath})` | the empty string, never throws (a deviation: Apple's returns the path's last component) |
| `attributesOfItem({atPath})` | throws an `Error` (Apple's throws an `NSError`) |
| `contents({atPath})` | resolves `null`, never rejects (a file moved or deleted after it was picked reads `null` too) |
| `contentsOfDirectory({at, includingPropertiesForKeys})` | resolves an empty array (a deviation: Apple's throws) |
| `removeItem({at})` | does nothing (a deviation: Apple's throws) |

A missing label or a wrong type is a `TypeError` in all of them. Two listings of one folder, the second started before the first has finished, share one read and answer the same URLs; a folder released by `removeItem` while it is being listed answers `[]` to both, and nothing of its children stays registered. Registered files are held until `removeItem`, which drops a folder together with every entry it listed, so an app removes what it has uploaded or cleared. `displayName` is user data: show it as text, never as markup.

### UIDocumentPickerViewController

`new UIDocumentPickerViewController({forOpeningContentTypes: [UTType.pdf], asCopy: true})` is the browser's file input, with `allowsMultipleSelection` (default `false`) and a `delegate`; both labels are required. Presenting it with `presenter.present(picker, {animated: true})` opens the input and leaves the page's root controller alone, so it has no view and sends no appearance hooks; `completion` runs once the input is open. It must be presented from the user's tap, like `UIPasteboard`'s write: a browser opens a file chooser for nothing else, so where the browser reports user activation (`navigator.userActivation`) a present without one is reported as a cancel at once, and opens nothing. The input is opened with `click()`, not `showPicker()`, which WebKit accepts on a file input and opens nothing for. The delegate's `documentPickerDidPickDocumentsAtURLs(controller, urls)` gets the chosen files as `file:` URLs, in the order the user chose them, and `documentPickerWasCancelled(controller)` follows a dismissal; both are optional; a delegate that still carries the retired name `documentPickerDidPickDocumentsAt` is refused with a `TypeError` naming the replacement, because a method under it would never be called. The URLs are not loadable: they resolve only through `FileManager` (name, size, bytes), and each is held until `FileManager.default.removeItem({at: url})`.

The content types become the input's `accept` (extension and MIME type for each; `image/*` for `UTType.image`; nothing at all when one is `UTType.item`). `UTType.spreadsheet` and `UTType.archive` have no extension of their own, so they stand for the types under them: the spreadsheet is `.xls`, its MIME type, `.xlsx` and its MIME type, and the archive is `.zip` and `application/zip`; none of them allows every file. A folder type (`UTType.folder`, alone) opens the browser's directory picker, the input's `webkitdirectory`, which the framework sets and draws, with no `accept`: the delegate gets one `file:` URL for the chosen folder, which `FileManager.default.contentsOfDirectory({at: url, includingPropertiesForKeys: null})` lists, nested folders included, as it lists a dropped one; a folder among file types adds nothing, since one input cannot pick both, and a browser that cannot say what is in an empty folder reports it as a cancel. `asCopy: false` throws a `TypeError`, because a page can only ever receive copies. `accept` is a hint the user can override, and the picker never checks that a file matches the types: check the name and size before reading, and keep the server's validation authoritative. The input's `cancel` event needs Chrome 113+ or Safari 16.4+, so in an older browser `documentPickerWasCancelled` is never called. The input is attached to the body, hidden, while it is open and removed when the user chooses, cancels, presents again or the picker is disposed.

### UIDropInteraction

`view.addInteraction(new UIDropInteraction({delegate}))` takes files dropped from the system on the view's element. The browser's drag events become Apple's delegate methods, named with the labels concatenated and the arguments positional, the interaction first: `dragenter` is `dropInteractionCanHandleSession(interaction, session)` and then `dropInteractionSessionDidEnter`; each `dragover` is `dropInteractionSessionDidUpdate`, whose `new UIDropProposal({operation: UIDropOperation.copy})` lets the drop happen (it prevents the default and sets `dropEffect` to `copy`, and `.move` does the same with `move`), while `.forbidden` and `.cancel` prevent it too and set `none`. As on Apple, a delegate with no `dropInteractionSessionDidUpdate`, or one that answers anything but a `UIDropProposal`, gives `.cancel`: the drop is swallowed and `performDrop` does not run, so a delegate that accepts files implements `dropInteractionSessionDidUpdate` and answers `.copy`; `dragleave` is `dropInteractionSessionDidExit`, once however many children the pointer crossed; `drop` is `dropInteractionPerformDrop`, then `dropInteractionConcludeDrop`, then `dropInteractionSessionDidEnd`. Every method is optional: without `canHandle` every drop is handled, and only an explicit `false` refuses one, but a drop is performed only when `dropInteractionSessionDidUpdate` answers `.copy` or `.move`. `canHandleSession` runs at each enter, and one session object goes from an enter to the drop. A drag that leaves the view and comes back is a new session: the one it left ends (`dropInteractionSessionDidEnd`), `canHandleSession` runs again and the delegate gets a new session object, so what it kept from the first is not the second's, where Apple's session continues across the exit. A refused drop is swallowed, never left to the browser: while the pointer is over the view its `dragover` and `drop` call `preventDefault` and set `dropEffect` to `none`, so the browser does not open the file in the tab, and no other callback follows; the same holds for a drop whose last proposal was `.forbidden` or `.cancel`, which never reaches `performDrop`. In nested views only the innermost interaction that accepted the drag decides the `dragover` and handles the drop, so one drop is performed once: an outer interaction only ends its session (`dropInteractionSessionDidEnd`), and one whose view an inner interaction refused handles the drop itself. A session that left the view ends with the next drop or drag end anywhere on the page, or when another drag enters, and `removeInteraction` or disposing the view ends one in flight; the document carries the interaction's listeners only while a session lives. An interaction added to a second view leaves the first, as Apple's does. The name `dropInteractionCanHandle` is retired: a delegate that carries it is refused with a `TypeError` naming `dropInteractionCanHandleSession`, because a method under the old name would never be called.

`session.items` are the files the drag carries (a string or a link is not an item), each a `UIDragItem` (`new UIDragItem({itemProvider})`, whose label is required) whose `itemProvider` is an `NSItemProvider`: `hasItemConformingToTypeIdentifier(id)`, `suggestedName` (the name without its extension, as Apple's) and `loadFileRepresentation({forTypeIdentifier, completionHandler})`, whose `(url, error)` handler runs after the call returns with a `file:` URL that `FileManager` reads, exactly as for a picked file; remove it with `FileManager.default.removeItem({at: url})`. `session.hasItemsConforming({toTypeIdentifiers})` is true when any item conforms to any of them, as Apple's is; a delegate that wants only those items filters `session.items` with `hasItemConformingToTypeIdentifier`. While the drag is over the page a browser shows only each item's kind and MIME type, so at enter `session.items` carries one item per file with a provider that answers conformance from those, `canHandleSession` decides by type and count, and nothing loads; the same `session` object and the same items load their files in the drop, which is the only time a browser gives them, and each item's `NSItemProvider` gains its file in place, so a provider captured at enter loads in `performDrop` too. A check that needs the files, a size for example, belongs in `performDrop`, which can refuse without reading: load the representation and ask `FileManager.default.attributesOfItem`, which never reads the bytes. A dropped folder is one item that conforms to `UTType.folder`, and its URL is a directory that `FileManager.default.contentsOfDirectory({at: url, includingPropertiesForKeys: null})` lists, each entry registered as it is listed; the framework does not expand folders, so an app that wants every file recurses in `performDrop`, and any depth or count limit is its own.

## Breaking changes

1.9.0 brings the controls, drag and drop, files and the application lifecycle to Apple's names and behaviour. A name that was renamed is refused where it is assigned, with a `TypeError` that names the replacement and the version, so a dead hook never goes quiet. The 1.6.0 renames (`pickerViewTitleForRow`, `pickerViewDidSelectRow`, `tableViewCommitEditingStyleForRowAt`, `numberOfItemsInSection`, `collectionViewDidSelectItemAt`) are still refused, quoting 1.6.0.

Behaviour that now follows Apple, with no name to change:

- A refused drop, a drop whose proposal was `.forbidden` or `.cancel`, and a delegate that gives no proposal (Apple's default is `.cancel`) are swallowed: the browser does not open the file and `performDrop` does not run. A delegate that accepts files answers `.copy` or `.move` from `dropInteractionSessionDidUpdate`.
- In nested drop views only the innermost accepting interaction performs the drop, once.
- A text field's paste runs the transform, then asks `textFieldShouldChangeCharactersInRangeReplacementString`, and `false` cancels the insertion.
- A table delegate receives `scrollViewDidScroll`, and a tap in single selection selects the row, sending `didDeselect` to the previous row and then `didSelect`.
- `.spreadsheet`, `.archive` and `.folder` in a document picker no longer allow every file.
- `UIDatePicker.valueChanged` is sent only when the date changed, and not at all while the picker is disabled; changing `datePickerMode` keeps the date.
- `textField.delegate = null` stops its delegate calls instead of throwing, and the range of a deletion with a caret is what the key removes (the grapheme cluster, word or line), not an empty range at the caret.
- `UISearchTextField` sends `editingDidBegin` and `editingDidEnd` when its input gains and loses the focus, so its Interface Builder default (`editingDidEnd`) fires; focusing a field that already has the focus, or blurring one that doesn't, sends nothing.
- A button copied from another's configuration keeps its title, and `title({for})` on a nib button reads its markup's text.
- A scroll view's delegate set before the view is placed is observed once it is.

## Limits

What this package leaves out or does differently on purpose, in one place (each is also said where its interface is):

- `DispatchGroup.notify(callback)` stands in for Apple's `notify(queue:execute:)`, because there is no `DispatchQueue`. `wait()` and `wait(timeout:)` are absent on purpose: they block the calling thread, and a browser has one main thread, which they would freeze.
- `UIView.frame` and `bounds` are read-only, because the stylesheet owns geometry, so there are no animatable size changes inside `UIView.animate`.
- `UIApplication.canOpenURL` and `open` accept `http(s):`, `mailto:` and `tel:` only; `itms-apps:` and other app schemes are refused.
- `PDFDocument(data:)` has no load signal to mirror: Apple's initializer is synchronous and posts no notification, so `pageCount` is 0 until pdf.js has loaded, and an app that needs a count before it displays the document uses its own validator.
- `UIToolTipInteraction`: where the tooltip sits is the site's stylesheet's, Apple has no placement API.
- Two `UITableView` cell classes that share one nib share the row element, so each class must set every state it draws in its own configure step. A tap selects the row in both selection modes, as on Apple, and the framework draws it as the `selected` class on the row; what that looks like, if anything, is the stylesheet's.
- `UIScreen.main.nativeScale` is `devicePixelRatio` and `nativeBounds` is `screen.width` by `screen.height` times it, in pixels as on Apple, at the origin, read on every use; `nativeBounds.width / nativeScale` is `screen.width`, which is how an app asks the device's width in points apart from the viewport's (`bounds`, which is `innerWidth` by `innerHeight`). Apple's `nativeBounds` is fixed to the portrait orientation and does not change when the device rotates; a browser's `screen.width` and `screen.height` follow the current orientation, so on a device that rotates they are what the browser reports then, usually with the axes swapped, and a zoom changes `devicePixelRatio` and with it `nativeScale`. Code that needs a portrait-fixed size takes the smaller and the larger of the two itself.
- `UIWindow` cannot be constructed, `UIApplication.windows` is always the one window, and there are no scenes: `UIApplication.shared.keyWindow` is the iOS 13 deprecated name, kept because the page has nothing to replace it with.
- Window blur and focus are not mapped to `willResignActive` and `didBecomeActive`: a browser fires them on every devtools or iframe focus change, so the lifecycle follows the page's visibility alone.
- `CGColor` is the string `UIColor.cgColor` returns, not a Core Graphics object, because the stylesheet is what draws: `CALayer.borderColor` takes and returns it, and a `UIColor` is refused. `resolvedColor` throws for a token the theme lacks instead of returning the receiver.
- `CADisplayLink.duration` is estimated from recent frame deltas, as a browser does not report the display's refresh interval; `RunLoop.current` is the main loop, as a page has one thread.
- `UIColorWell`: the browser's control has no alpha, so a pick keeps the previous colour's alpha.
- A static `disabled` attribute in a nib starts a control disabled, as in HTML, because `isEnabled` reads the element's attribute.
- `UIDatePicker`'s teardown relies on jQuery UI's internal `"datepicker"` data key (the page pins jquery-ui 1.13.3): re-check it on any jQuery UI bump.
- `UIDatePicker.date` can be `nil`, which Apple's cannot: a web date input is cleared by its user and the sites use the empty value for "no filter". `UIDatePicker.Mode.countDownTimer` exists and is refused on assignment, as a page has no duration control.
- `UIButton.Configuration`'s `.plain()`, `.filled()`, `.tinted()` and `.gray()` are the same value, and `showsActivityIndicator` neither hides the title nor disables the button, as on Apple: the look is the stylesheet's, from the `activity-indicator` attribute, and the double-press guard is the app's `isEnabled`. `NSDirectionalRectEdge` has the four edges only.
- `UITextContentType` has the 17 cases of `UITextField.textContentType`. Apple's others are not published: `namePrefix`, `middleName`, `nameSuffix`, `nickname`, `jobTitle`, `streetAddressLine1`, `streetAddressLine2`, `birthdate`, `birthdateDay`, `birthdateMonth`, `birthdateYear`, `creditCardSecurityCode`, `creditCardName`, `creditCardGivenName`, `creditCardMiddleName`, `creditCardFamilyName`, `creditCardExpiration`, `creditCardExpirationMonth`, `creditCardExpirationYear` and `creditCardType` have a WHATWG token and can be added when a page needs one; `location`, `sublocality`, `addressCityAndState`, `shipmentTrackingNumber`, `flightNumber`, `dateTime`, `cellularEID` and `cellularIMEI` have none. `autocomplete="off"` has no Apple case either.
- `UIAccessibilityTraits` publishes `button`, `link`, `header`, `selected` and `notEnabled`; the other traits are unmapped (listed under Accessibility above).
- `accessibilityTraits` is an array of the active cases, as `UIControl.state` is, where Apple's are option sets, which JavaScript lacks.
- An `addTarget` pair and an `@IBAction` connection keep their own DOM policies: a pair stops its event at the control, an `@IBAction` does not and cancels a click's default (except on a checkbox or radio), because changing the second would alter every existing action, the document-click menus among them. A site that moves an `addTarget` to an `@IBAction` checks that nothing above the control handles that event.
- An `@IBAction` whose sender is not a `UIControl` (a plain `UIView`) keeps the click handler it always had, since it has no control events.
- `UIApplication`'s `didBecomeActive` at launch is posted once, at the first task after load, and the launch runs when the module is evaluated: an observer added in the first `viewDidLoad` of a page that presents after its own session fetch does not hear it. Posting it after the first `present` or `restore` completes would be closer to Apple's and would change a public lifecycle order, so it is not done.
- A drag that leaves a `UIDropInteraction`'s view and comes back is a new session (the old one ends, `canHandleSession` runs again): without a `drop` or `dragend` a page cannot tell it is the same drag.
- A `UITableView`'s scrolling, and `isScrollEnabled` on it, come from the stylesheet's `overflow`, as Controls says for `UIScrollView`, where Apple's scroll view owns them.
- `CALayer.borderWidth` grows the box, as the stylesheet's border does, where Apple draws the border inside it: drawing it inside would move the fields that use it by a pixel. This is kept as it is until it is decided whether to match Apple.
- `UIDatePicker.datePickerMode` defaults to `.date`, where Apple's default is `.dateAndTime`: Apple's would turn the sites' date-only fields into datetime fields. This is kept as it is until it is decided whether to match Apple.
- `new UIButton()` has a plain `configuration`, where Apple's is `nil`: a `nil` would make `button.configuration.showsActivityIndicator = true` throw on a code-made button.
- When a `UITextField` or `UISearchTextField` delegate's `textFieldShouldEndEditing` returns `false`, the blur still sends `editingDidEnd`, and taking the focus back on the next tick sends a new `editingDidBegin`; Apple sends neither. A browser cannot cancel a blur.
- `FileManager.displayName({atPath})` is the empty string for a path with nothing at it, where Apple's returns the path's last component. `contentsOfDirectory` and `removeItem` do not throw for a path that is gone, where Apple's do (see the FileManager table). This is kept as it is until it is decided whether to match Apple.
- `UIApplication.shared.keyWindow.subviews` is empty: linking the root view into the window would lay it out twice.

## Sample

`sample/` is a small app with a menu of pages, one per part of UIKit: buttons, labels, text fields, a custom view with its own nib (also bound through a subclass), a table view with a custom cell, since 1.4.0, links through `userActivity`, `UIImage(systemName:)`, `UIScrollView` offsets and key commands next to a text field, since 1.5.0, a Traits page with a badge configured through `@IBInspectable`, `CGRect` frames and bounds, and the size-class hooks on resize, since 1.6.0, a Navigation page whose root is a `UINavigationController`, pushing a detail controller and popping it from the bar, from the page and with the browser's back button, and, since 1.8.0, a PDFKit page with a `PDFView` showing a two-page document, both delegates, the four `PDFDocumentDelegate` find methods and `PDFViewDelegate`'s link interception, page buttons gated by `canGoToNextPage` and `canGoToPreviousPage`, and the `displayMode` and `displayDirection` pair. It depends on this package through `file:..`, so it runs against the working tree, and loads Font Awesome for the symbol images. Run `npm install` at the repo root first: npm does not install a linked package's own dependencies, so `pdfjs-dist` has to come from there, and without it the build stops with a module-not-found at `src/PDFKit.js`.

```
npm install
cd sample
npm install
npm start
```

Then open http://localhost:8080.

## Tests

```
npm test
```

Each test file picks its page. A file that only exercises lifecycle, responder chain or observer bookkeeping imports `./setup.js`, a chainable jQuery stand-in that remembers the html it was given. A file that binds outlets, resolves nib roots, dequeues table rows or dispatches DOM events imports `./dom.js`, which installs a jsdom document and the real jQuery and exports `page(html)` to start from a body of its own. Node runs each file in its own process, so the two never meet; a file imports one of them and never both. `npm test` also regenerates `types/` and `eslint/globals.cjs`, which are committed. To run one file, use `node --import ./test/register.mjs --test test/pdfkit.test.js`, not `node --test` alone: PDFKit's modules import pdfjs-dist, whose viewer evaluates against `document`, so `test/register.mjs` maps those specifiers to fakes, and `pdfkit.test.js` and `frameworks.test.js` need it (`npm test` passes it).
